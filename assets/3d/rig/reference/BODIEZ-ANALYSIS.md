## 1. 骨架布局（74 / 71 骨）

```
Root
└── UI_Panel                              ← 所有滑块的父骨
    ├── Body_Type   Hip_Wide   Tall_Short   Shoulder_Type        ← 非形变骨（11 根）
    ├── Body_Size   Arm_Size   Leg_Size     Head_Size
    └── Breast_Size                                              ← 仅女性
Root
├── spine → spine.001 → … → spine.006      ← ⭐ **7 节脊柱**
│   ├── spine.003 → shoulder.L/R → upper_arm → forearm → hand
│   │                → palm.01~04 → f_index/f_middle/f_ring/f_pinky（3 节）+ thumb（3 节）
│   │                （palm.01 同时带 thumb）
│   └── spine.003 → breast.L/R（仅女性）
└── spine → thigh.L/R → shin.L/R → foot → toe
```

| 事实 | 值 |
|---|---|
| 骨数 | 女 **74** = 变形骨 63 + 非形变骨 11；男 **71** = 61 + 10 |
| **Rigify 生成** | ✅ 有 `rigify_colors` / `rigify_target_rig` / `rigify_widgets_collection`；**女性文件里 `rigify_rig_basename = rig_modular_male`** → 女性骨架由男性 metarig 派生 |
| **控制骨 / IK** | ❌ **没有** —— 名字里带 `ik`/`fk`/`tweak`/`master` 的骨 **0 根**；但有 74 个 `WGT-*` 网格对象**没对应骨** → 是**残留件** |
| **头/颈骨** | ❌ **没有** —— `spine.006` 主导 **416 个顶点**（z ∈ **[87.4%, 100.0%]H**），**头部 100% 权重在它上面** |
| 命名 | **Rigify 风格**（`spine.001` / `shin.L` / `upper_arm.L`），**不是** UE 风格 |
| 男女 | **两套不同骨架**（女多 `breast.L/R` + `Breast_Size`） |

**网格**：女 `Geo_Female_White_Body` 5256 v / 5254 面（**全四边形**）；男 5466 v。
**男女拓扑不同** → 服装件也不能跨性别复用。
**修饰器**：`ARMATURE` + **`SUBSURF`（viewport 1 / render 2）** → 5256 是**控制笼**，交付时细分到 **≈84,064 四边形 ≈168k 三角面**。

## 2. 变形机制（两层，都自包含在文件里）

### 2.1 体型（胖瘦/肌肉/臀宽/胸）= **shape key + `SCRIPTED` 驱动器**

**滑块骨当前值**（= `pose.location.x`）—— 女性文件带**未复原的编辑状态**：

```
Body_Type +0.0024   Hip_Wide 0.0000   Tall_Short −0.0922   Shoulder_Type +0.0085
Body_Size 0.0000    Arm_Size 0.0000   Leg_Size   0.0000   Head_Size +0.0855   Breast_Size −0.0763
（男性文件全部为 0）
```

**9 个 shape key（女）/ 7 个（男）**，其中 **7 条 `SCRIPTED` 驱动器**（⚠ **挂在 `Key` 数据块上，不在对象级、也不在骨架上** —— 这是最初两次探查漏掉它的原因）：

```python
# 体型预设：一根滑块切 4 档 —— 【区间带硬切换】
Regular  = 1 if (var >= 0    and var < 0.1 ) else 0
Thin     = 1 if (var >= 0.1  and var < 0.25) else 0
Muscular = 1 if (var >= 0.25 and var < 0.3 ) else 0
Fat      = 1 if (var >= 0.3  and var < 0.45) else 0
# 连续轴
Hip_Wide     = var + 0.0
Breast_Big   = var + 0.0      # ⚠ 两个语义相反的通道
Breast_Small = var + 0.0      #    被【同一条表达式】驱动
```
驱动器变量：`TRANSFORMS`，`bone_target = Body_Type / Hip_Wide / Breast_Size`，`transform_type = LOC_X`，`space = LOCAL_SPACE`。

**各通道强度（相对 Basis 的最大顶点位移）：**

| 通道 | 女 | 男 |
|---|---|---|
| `Regular` | **25.28 mm**（value=1.0） | **0.00 mm**（value=1.0） |
| `Thin` / `Thin_old` | 29.59 / 25.26 mm | 17.36 / 24.10 mm |
| `Muscular` | 46.25 mm | 50.32 mm |
| **`Fat`** | **87.30 mm** | **92.45 mm** |
| `Hip_Wide` | 26.68 mm | 22.54 mm |
| `Breast_Small` / `Big` | 5.47 / 10.44 mm | — |

### 2.2 比例（高矮/头大小/臂长/腿长/肩型/整体大小）= **`ACTION` 约束 + 手摆 20 帧动作**

⭐ **这是最初漏掉的机制，也是它最值钱的设计**：

```
12 个动作：deform_body_tall / _short / _small   deform_head_big
           deform_arm_small   deform_leg_small  deform_palm_wide
           deform_shoulder_wide / deform_shouler_narrow（作者拼错了 shouler）
           deform_breast_big / _small    + 1 个烘焙用动作

每根受影响的变形骨挂一条 ACTION 约束（女 63 条 / 男 61 条）：
   action            = deform_body_tall
   subtarget         = Tall_Short            ← 读滑块骨
   transform_channel = LOCATION_X
   min / max         = 0.0 / ±0.2            ← 滑块行程
   frame_start / end = 1 / 20                ← **20 帧姿态**
   mix_mode          = BEFORE_FULL           ← 多条可叠加
9 个滑块骨各有一条 LIMIT_LOCATION 限定行程
```

**设计思路**："**滑块位置 = 动作时间轴**" —— 作者**手工摆 20 帧姿态**存成动作，滑块一拖就在动作里插值。**完全自包含，不需要插件。**

### 2.3 实测补充：滑块的实际行程与基础姿态

**复位后**（骨架 scale 1.0、全部滑块 0 → `Body_Type = Regular`）：**身高 1.4972 m**（网格局部）。

**`ACTION` 约束在 headless Blender 里确实求值** —— `Tall_Short` 扫掠：

| 滑块值 | −0.20 | −0.10 | **0.00** | +0.10 | +0.20 |
|---|---|---|---|---|---|
| 身高 (m) | **1.1539** | 1.3255 | **1.4972** | 1.6825 | **1.8751** |

→ **跨度 ±25%**（1.15 ~ 1.88 m），**线性**。比我们契约的 ±8% 大一倍多。

**其余滑块**：`Arm_Size` / `Shoulder_Type` / `Hip_Wide` / `Breast_Size` **对身高无影响** ✓（正确行为）。
⚠ 但 `Body_Size` +0.1 **降 3.7 cm**、`Leg_Size` +0.1 **降 4.6 cm** —— **方向反了**（命名与动作帧映射可能不一致），
**这是它的又一处不规范**。

**`Body_Type` 确认是区间带硬切换**：`t=0.05→Regular`、`0.15→Thin`、`0.27→Muscular`、`0.35→Fat`
—— **0.10 / 0.25 / 0.30 三处跳变，没有中间态**。

⭐ **基础姿态是 A-pose，不是 T-pose**（这是 SPEC **F37** 的来源）：

```
女  上臂俯角 +47.7°   →  摆平后 0.0° ；臂展 1.2066 → 1.6443 m ；臂展/身高 0.7098 → 0.9672
男  上臂俯角 +51.5°   →  摆平后 0.0° ；臂展 1.2147 → 1.6637 m ；臂展/身高 0.6941 → 0.9507
```

⚠ **摆平后腋下有可见拉伸**（线性混合蒙皮，47° 大角度 + 低模）→ 所以参考图要**两种姿态都出**：
**A-pose 版**（解剖干净 → 主用于喂生成器）+ **T-pose 版**（姿态合契约、臂展数可信 → 作姿态提示并注明忽略腋下）。

⚠ **我一度把这里写错过**：早期版本报的是 **女 0.9153 / 男 0.9878**，并据此得出
「女性臂展偏短 7~8%、不满足共用 rest」的结论 —— 那**全是错的**，根因是我的旋转 bug
（`Matrix.Rotation` 绕**世界原点**，手臂被连同位移转走）。更正后见上面数字，**两性都在契约容差内**。
详见 SPEC **F38**。

### 2.4 男女两具的对比 —— ⭐ 臂展暴露了「不能共用 rest」

| | 女 | 男 |
|---|---|---|
| **复位后网格高**（两具差 **1.29×**！） | 1.4972 m | **1.9274 m** |
| 缩放到契约身高的系数 | ×1.1354 → 1.70 | ×0.9080 → 1.75 |
| A-pose 上臂俯角 | +47.7° | **+51.5°** |
| A-pose 臂展/身高 | 0.7098 | 0.6941 |
| ⭐ **T-pose 臂展/身高**（**更正后**） | **0.9672** ✅ | **0.9507** ✅ |

**结论（已更正）**：
- **两性臂展都在契约容差 `1.00 ± 0.04` 内**（女 0.9672 / 男 0.9507）→ **臂展这一项它没有问题**。
- 真正说明"两套各自独立的件"的是**另外三处**：**复位高差 1.29×**（1.4972 vs 1.9274）、
  **骨架 74 vs 71 骨**、**拓扑 5256 vs 5466 顶点**。
- ⭐ 因此保留 **「T-pose 臂展/身高 = 1.00 ± 0.04」为契约判据**
  （[`race.json`](../races/humanoid/race.json) `proportions.arm_span_over_height`）——
  它虽是 D3 共用 rest 的前提，但**用它当尺子时必须先保证自己的测量是对的**（SPEC **F38**）。

### 2.5 围度实测 —— ⭐「腰太瘦」被量化证实

**软尺量法**（水平切片 → XY 凸包周长；⚠ 已按 SPEC F38 剔除手臂/手指顶点 + 关 SUBSURF）：

| 预设 | 女 胸/腰/臀 (1.70 m) | 女 WHtR | 男 胸/腰/臀 (1.75 m) | 男 WHtR |
|---|---|---|---|---|
| Thin | 66.2 / 56.7 / 79.7 | 0.3337 | 88.5 / 64.2 / 67.8 | 0.3669 |
| **Regular** | **74.7 / 63.8 / 86.8** | **0.3751** | **90.9 / 72.0 / 74.7** | **0.4113** |
| Muscular | 93.5 / 68.9 / 96.4 | 0.4052 | 103.8 / 79.1 / 88.0 | 0.4521 |
| Fat | 99.2 / 104.2 / 125.1 | 0.6128 | 111.6 / 116.6 / 111.6 | 0.6665 |

- **现实健康区间 WHtR = 0.40 ~ 0.49**（WHO 建议 < 0.50）
- ⭐ **女 Regular = 0.3751 → 低于健康区间下端** ⇒ 用户说的「腰太瘦」**成立且可量化**
- 男 Regular = 0.4113 → 在**下限附近**，也偏瘦
- ⚠ **它的预设是区间带硬切换** → Regular(63.8) 与 Muscular(68.9) 之间**没有中间档**，
  **「稍微加粗一点」它做不到**（Muscular 还会把颈围从 64.1 拉到 90.7，是另一个体型而非"腰粗一点"）
- ⭐ 所以本仓库把 **WHtR 立为判据**：**女 0.42 ± 0.02（71.4 cm @1.70）／ 男 0.45 ± 0.02（78.8 cm @1.75）**
  —— 都在健康区间内、比 Bodiez 加粗约 7 cm，且靠**我们自己的 tent 连续插值**可以停在任意中间值。

⚠ 另注：**别用骨头位置量头高** —— 用 `spine.006` 的骨位算出的是 **10.32 头**（错），
因为骨的**影响范围**从颈部就开始了，而骨的**原点**在头内部。头高必须用**权重边界或几何**量（得 **12.6%H ≈ 8 头** ✓）。

## 4. 与我们的对照：学什么、别学什么

### ✅ 借了（已写进契约）

| # | 借鉴 | 落在哪 |
|---|---|---|
| 1 | **滑块骨 UI**（参数骨 + `custom_shape` + `LIMIT_LOCATION`，不用写面板） | [`race.json`](../races/humanoid/race.json) `slider_bones` |
| 2 | **多通道体型**（4 预设 + 臀宽 + 胸）比单轴胖瘦表达力强 | [`channels.json`](../channels.json) |
| 3 | **7 节脊柱**（躯干比例与弯曲更细腻） | `profiles/humanoid_biped_7spine.json`（65 → **77 骨**） |
| 4 | **每指掌骨**（抓握/张开更自然） | 同上（拇指**不加**掌骨，与 VRM 一致） |

### ⭐ 借了但**改了**（它的缺陷）

| 它的做法 | 我们的改法 | 理由 |
|---|---|---|
| 体型用**区间带硬切换** `1 if a<=t<b else 0` | **tent 连续插值** | 它**拖动时体型跳变**，且永远停在预设上、不能停在中间 |
| `Breast_Big`/`Breast_Small` **同一条表达式** | **单个有符号通道** `BS_Breast` | 同值驱动两个语义相反的通道，语义错 |
| 比例用 **`ACTION` 约束** | **骨缩放 + 身高归一化** | ⚠ **glTF 没有约束** → 导出时全部消失，交付前必须烘 |
| 滑块**绝对值 + 不对称行程**（`Tall` `[0,+0.2]` / `Short` `[0,−0.2]`） | **以 0 为中心、对称行程** `[−1,+1]` | 它因此**一个滑块要两条动作**（女 63 条约束大半源于此） |
| `Basis` 不是标准体型（女靠 `Regular=1.0` 才成立，25.28 mm 偏移；男 `Regular` 是 **0 mm 空档**） | **Basis 就是标准体型**（默认值 0 = 正确形态） | 男女不一致，且**驱动器一旦失效女性就变形** |

### ❌ 不借

| 不借 | 理由 |
|---|---|
| **它的资产**（网格 / 骨架 / 体型数据） | ✅ **有许可** —— 但**我们主动选择自研**（见 §6）：自研能拿到统一骨架 / 我们自己的命名 / 可控拓扑，这些是"直接用它"给不了的 |
| **它的骨架分叉**（女 74 / 男 71） | 违反 D3「男女共用一副 rest」→ **动画不能零重定向**、工具链翻倍 |
| **它的命名**（Rigify 风格） | 与 UE/Mixamo 的对齐度下降；且我们现有工具链全建在 UE 风格上 |
| **它的 `ACTION` 约束机制** | glTF 不保留（见上） |

### ⚠ 它文件里的两处"不干净"（**别拿它的数值当参考**）

1. **女性文件保存于编辑中状态**：骨架对象 `scale = 1.3136`（男性 1.0），多个滑块值非零（男性全零）
   → 世界身高变成 **女 1.968 m / 男 1.532 m**（**反了**）。**网格局部高度**才是 女 1.498 / 男 1.532 m。
2. **`Geo_Male_White_Ear` 是坏的**：`parent = None`、**Armature 修改器的 object 是空的**、
   **187 个顶点组全是 `DEF-*`，骨架里一根都没有**（187/187 都不存在）→ **完全没绑上骨架的残留件**。

## 5. 一条有用的旁证：接缝位置

它的头部（`spine.006` 主导顶点）下界在 **87.4%H**，且颈部顶点密度最低点在 **86–88%H**。
与我们现有库的 `Head` 骨（**87.3 / 87.9%H**）与 8 头 canon 下颌（**87.5%H**）**三源汇合**
→ 接缝定在 **87.5%H**（见 [`race.json`](../races/humanoid/race.json) `head.seam_height_pct`）。

**并且它的头占 `[87.4%, 100%] = 12.6%H`**，而 8 头身的头高应是 12.5%H → **它也是 8 头身**。

⚠ **但它颈部没有现成的边环**：84–91%H 区间"两端 z 差 < 0.5 mm 的水平边"**总共只有 34 条、全是零散 2 条一组**，
最接近 87.5%H 的只有 2 条 → **若要从它身上砍头会得到锯齿开口，必须重做一圈回环**。

## 6. 许可与处置（**已明确：有许可；我们主动选自研**）

- ✅ **该件有许可**（用户确认）。所以它**可以用**，不存在"不能用"的问题。
- **但本仓库仍然只把它当参考件、不引进生产资产**，理由是**技术性的**，与许可无关：

| 若"直接用它" | 代价 |
|---|---|
| 骨架 | ❌ **男女分叉**（女 74 / 男 71）+ 命名是 Rigify 风格 → 违反 D3、动画不能零重定向、工具链翻倍 |
| 头/颈 | ❌ **没有头颈骨**（头 100% 权重在 `spine.006`）→ 二次元必需的**眼睛追踪/面部朝向**做不了 |
| 体型 | ❌ 是**手作的 9 个 shape key**，表达力固定（改预设要手工雕）；且 `Basis` 不是标准体型（女靠 `Regular=1.0` 才成立） |
| 比例 | ❌ 靠 **`ACTION` 约束** → **导出 glTF 时全部消失**（SPEC F36） |
| 拓扑 | ❌ **男女拓扑不同**（5256/5466）+ **SUBSURF 2 级** → 交付体积大一个量级 |
| UV/贴图 | ❌ **零贴图、7 层 UV 里 5 层是空壳**（含 `face_main`）→ **省不了事** |

**⭐ 结论**：**它最值钱的是"做法"，不是"资产"。** 而"做法"我们**已经全部吸收**（见 §4）——
**自研能拿到这些东西，同时拿到统一骨架、我们自己的命名、可控拓扑与可控体积**，这三样恰恰是"直接用它"给不了的。

> **`download/bodiez/` 保留**（`download/` 是"还没决定去留的原始下载"，不随手清）；
> **但没有任何代码/契约依赖它** —— 映射表的骨表已改为读我们自己的 `profiles/`。

## 7. 结论
