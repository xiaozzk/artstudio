# 3D 角色管线 v2 —— 体形 morph 契约（SPEC）

> **本文件是接口契约，所有工具/资产/预览必须按此实现。**
> 维护者：**Lead**。任何改动都要同步通知全体成员（改动会破坏别人的代码）。
> 版本：**v1.0**（2026-10-13 冻结）

---

## 0. 一句话

**体形差异 = morph（偏移表）；身高差异 = 骨架等比缩放。**
身体与服装各自持有**同名同序**的 morph，运行时由**一个数值**同步驱动。

## 1. 为什么是这个架构（侦察依据，别再重新论证）

本节是本 session 的实测结论，是整套设计的**事实基础**：

> **硬规则（F6）**：对每根体形骨 B，把 B 的**全部直接子骨**设 `inherit_scale = 'NONE'`，
> 使缩放 B **只影响 B 自己的权重区域**，不沿链传递。**这一步不做，派生形状必然失控。**

>
> | 阶段 | 文件 | `inherit_scale` | 为什么 |
> |---|---|---|---|
> | **烘焙期**（摆体形骨 → 烘 shape key） | `bodies/*.blend`、派生过程中的临时状态 | **必须 `NONE`** | 不设 NONE，体形骨缩放会沿骨架链传下去（实测 `pelvis` 会让身高意外 +11.24%）。`tools/3d/bodyshape/derive.py` 会**自检并报错** |
> | **交付期**（会被引擎加载的运行时资产） | `garments/*.blend` | **应还原 `FULL`** | 保险：实测 root 骨 ×1.08 的拉伸离散度 **NONE 0.0257–0.0760 → FULL 0.0000–0.0001**。虽然 F12 已要求身高走**对象级**缩放（与 inherit_scale 无关），但还原 FULL 可让 root 骨路线也不失真 |
>
> **实测现状**：`bodies/*.blend` = `FULL 47 / NONE 18`（烘焙期状态，**符合本表**）；
> `garments/*.blend` = `FULL 65`（交付期状态，**符合本表**）。**两者都对，不要"统一"。**
> **走 B1 路线时**，`bodies/` 会变成运行时角色 → **交付前必须还原 `FULL`**。

### 3.3 morph 规范（**同名同序，最关键的契约**）

| shape key 名 | 索引 | 含义 | 目标系数 |
|---|---|---|---|
| `Basis` | — | 标准体 | — |
| `BS_Thin` | **0** | 瘦 | 0.86 |
| `BS_Heavy` | **1** | 壮/胖 | 1.16 |

* **索引顺序固定为 `BS_Thin` = 0、`BS_Heavy` = 1**，身体与每件服装必须一致。
* `Basis` 之外的**每个** shape key 都必须存在（即使是全零），这样索引对齐。
* 运行时权重 ∈ `[0, 1]`，**默认 0**（= 标准体）。

### 3.4 身高（**2026-10-13 已修正，原写法废弃**）

**身高不做 morph**，用**角色根节点 / 骨架对象的世界等比缩放**：

```
armature_object.scale = (h, h, h)      h ∈ [0.92, 1.08]
```

> ⚠ **不要用 `root` 骨缩放**（本节原写法）。它与 §3.2 硬规则**冲突**（verifier 实测，`assets/3d/rig/reports/verify-heightbug.json`）：
>
> | 配置 | 身高变化（要 +8%） | 拉伸比离散度（§5 阈值 ≤0.01） |
> |---|---|---|
> | 原写法：缩 `root` **骨**（§3.2 生效时） | 女 **+0.50%** / 男 **+0.44%** ❌ | **0.0841 / 0.0833 → 超标 8.4×** ❌ |
> | **✔ 本写法：骨架对象世界等比缩放** | **+8.00% / +8.00%** ✅ | **0.00003 / 0.00003** ✅ |
> | 只把 14 根体形骨**自身**设 NONE | −0.00%（身高纹丝不动，角色整体上浮 7.5 cm） | 0.000007 |
>
> **根因**：`root`→`pelvis` 是 FULL，但 §3.2 把 `pelvis` 的子骨（`spine_01`/`thigh_l`/`thigh_r`）设成了 `NONE`
> → root 的缩放**传不过 pelvis**，躯干与腿完全不缩放，只有骨盆那一圈被拉伸。
> **结论：F6（体形骨子骨设 NONE）与"缩 root 骨调身高"不能并存。**
> 对象级等比缩放**与 F6 无关**，两者天然正交 —— 这才是 §3.4 与 §3.2 能同时成立的原因。

## 4. 服装契约（`garments/*.blend`）

### 4.0 前置决策：走哪条路（**F10/F11/F16/F17 的最终结论**）

现有服装是按 **「Regular」身体**剪裁的，我们**没有** Regular 身体（包里只有它的贴图 + 裸露臂部皮肤）。
拿 Superhero 当标准体 → 像素法实测**裸露身体占剪影 女 63.3% / 男 74.2%**，厘米级外推只能降到 ~44%，**不可用**。

**三条路线，用同一把尺子比：**

| 路线 | 做法 | 需要额外资产 | 裸露身体 | 遗留工作 | 定位 |
|---|---|---|---|---|---|
| **B2** ⭐ | **体形 morph 派生在「角色自身网格」上** —— 用角色自己的 rig 摆体形骨、逐件烘 shape key | **无** | **无（结构性）** | **无** | ✅ **遗留资产主路线** |
| B1 | 标准体改用**同源（Regular 比例）身体**（Tripo 生成时指定，或从服装自带皮肤补全） | 一具同源身体 | 无（同源） | 生成身体 | ✅ **Tripo 阶段正式形态** |
| A | 保留 Superhero + **厘米级自动外推** | 无 | 74% → 44% ❌ | 真几何重塑（人工密集） | ❌ 不采用 |

**B2 的原理（F17）**：现有 `tryon/` 的最终角色 = **服装布料 9 件 + 服装自带皮肤 + 基础体的头 3 件**，
**共用服装自己的 rig** —— 最终角色里**根本没有 Superhero 身体**（它只捐一个头）。
→ 布料/皮肤/头**共用同一组骨变换**，体形一变三者**同构地一起变**，**结构性地不存在"身体与服装不一致"**。

**B2 实测（Lead，`task/007-morph-pipeline/lead/b2_report.json`）**：12 件 / 27,920 顶点（女）、27,637（男）；
身高比 **0.99891 / 1.00143**（女）、**0.99997 / 1.00020**（男）≈1.0000；最大位移 **4.21 / 3.82 cm**（v2 系数；v1 系数下为 3.21 / 2.91 cm）；
**morph 数据量 654 / 648 KB（两档全角色）**；三档顶点数一致；渲染视觉连贯、面无接缝。

**B2 的边界（必须知道）**：
1. 体形只由**布料 + 可见皮肤**表达 —— 躯干被衣服盖住，对这批资产合理。
2. ❌ **不能做"裸露躯干"的服装**（泳装/裸露护甲）：布料不包住躯干时，体形变化**没有载体** → 那时必须走 B1。
3. 每套服装是**自包含角色**（各带自己的 rig 与 morph），morph **不能跨套件复用**（单套仅 654 KB，可接受）。
4. Tripo 阶段身体与服装同源 → **B1 与 B2 收敛为同一件事**。

> **实现提示**：B2 下 §4.1 的"剥离皮肤面 / 贴合标准体 / 从身体传递 morph"**三步全部不需要** ——
> 直接在**角色自己的 rig** 上摆骨、逐件烘 shape key 即可（`b2_feasibility.py` 是一个 40 行的可跑参考）。
> §4.2 的传递算法仅在 B1 路线下才用得上。

### 4.1 处理链路（**B1 路线**用；B2 路线见 §4.0 的实现提示）

```
现有着装资产
   ↓ ① 剥离：按材质剔除 MI_Regular_* 的皮肤面 → 纯布料件
   ↓ ② 贴合：骨空间重绑到标准体（Regular rest → Standard rest）
   ↓ ③ 传递：把标准体的 BS_Thin/BS_Heavy 传到每件布料
garments/*.blend
```

**① 剥离**：判据 = 面所属材质名以 `MI_Regular_` 开头 → 删除该面。
**② 贴合**：对每个顶点，按其权重骨做 `RegularRest⁻¹ → StandardRest` 的骨空间变换（线性近似）。
**③ 传递**：重心坐标 + 三角面标架（见 4.2）。

### 4.2 传递算法（F8 已验证）

对每个服装顶点 `p`：

```
绑定（一次性）：
  近邻搜索 p 在【标准体 rest】网格上 → 三角面索引 t, 命中点 q, 法线 n
  w  = q 在 t 上的重心坐标
  F  = t 的标架 (n, t̂, û)
  o  = p - q 在该标架下的分量（三维）

求值（每个 morph 档）：
  P' = Σ wᵢ · V'ᵢ                    （变形后三角面的插值点）
  F' = 变形后三角面的标架
  p' = P' + o 在 F' 下重组
```

**必须**用 depsgraph 求值（F9）。绑定数据 ≈ 28 字节/顶点，一次性。

### 4.3 服装文件内容

* 网格：**纯布料件**（皮肤面已剥离），原点对齐世界 (0,0,0)
* 骨架：**共用标准体那副**（`Skeleton` 指向标准体；不做"每件一份 rig"）
* morph：`Basis` + `BS_Thin`(0) + `BS_Heavy`(1)，**与标准体同名同序**

### 4.4 不适用的件（必须显式列出，禁止硬做）

离身体过远的自由垂坠件（裙摆、披风、兜帽的悬空部分）近邻绑定会**绑错**。
→ 这类件**改为骨骼驱动**（挂到骨上），或在 manifest 里标记 `"morph": "skip"` 并说明理由。
**禁止**为了"全部覆盖"而硬做，导致穿模。

* **旧 `assets/3d/blend/`**：只读不改，作为 v2 的输入与回归基线。
* **未来 Tripo**：Tripo 只生成**标准体 1 次 + 每件服装 1 次**。
  瘦/壮由骨骼滑块派生（本 SPEC 的 §3.2/§3.3 直接复用），服装靠 §4.2 传递。
  → **切换到 Tripo 时，只需替换"标准体"和"服装基础网格"两个输入，其余链路不变。**
  这是本架构"为 Tripo 铺路"的具体含义。
